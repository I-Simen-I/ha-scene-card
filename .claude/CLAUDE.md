# HA Scene Card

A Home Assistant dashboard card (Lit 3, TypeScript, webpack): a row of
buttons, like a horizontal stack, that shows which scene is active. Each
button is an entity with a state; it's active while the entity is `on`.
Distributed as one file, `dist/ha-scene-card.js`, through the
Marketplace/HACS. Repo `I-Simen-I/ha-scene-card`; the build setup comes from
`I-Simen-I/simple-weather-card`. Code, commits, PRs, README, release notes,
tests and the examples in `dev/` dashboards are in English.

Personal, machine-specific notes go in `.claude/rules/personal.md` (not
committed; every file in `.claude/rules/` is loaded automatically).

## Maintainer

Claude is the main maintainer of this code. The repository owner decides
what the card should do, tests it in Home Assistant and releases it; the
code itself is Claude's responsibility. Work like an owner:

- Read the code around a change before writing any. Reuse what's there
  (`fireEvent`/`fireAction` in `src/actions.ts`, `toButton`/`buttonName`/
  `isTemplate` in `src/config.ts`, `computeCssColor` in `src/color.ts`, the
  helpers in `test/helpers.mjs`, Home Assistant's own elements and
  translations) instead of writing a second version. If something almost
  fits, change it so it fits both uses.
- Prefer less code: no options, abstractions or fallbacks the card doesn't
  need. Small functions with names that say what they do; comments for why,
  not what.
- Leave the code better than you found it. When a change makes code,
  options, tests or docs obsolete, remove them in the same change.
- Keep the code, tests, README, `dev/` and this file in step: a change isn't
  done until all of them match it.
- Say so when a request would make the code worse, and suggest a better way,
  before building it.

## Layout

- `src/ha-scene-card.ts` – the card: config, `hass`, layout.
  `src/button.ts` – `ha-scene-card-button`, one button with its state,
  icon and actions. `src/editor.ts` – visual editor, in the same bundle.
- `src/config.ts` – button helpers shared by card and editor, and the
  editor's entity domains. `src/actions.ts` – events and actions,
  `src/color.ts` – theme color names to CSS, `src/style.ts` – styles,
  `src/types.ts` – types only.
- `test/` – Node test runner. `card.test.mjs` and `editor.test.mjs` load the
  **built** bundle in happy-dom with a fake `hass` from `helpers.mjs`, so
  `yarn build` before `yarn test`.
- `.github/workflows/` – build (typecheck, lint, formatting, build, test,
  artifact), release (manual button), labeler, HACS validation.
- `dev/` – local Home Assistant in Docker for manual testing.

## Decisions

- No translations of our own: the editor's labels are Home Assistant's
  (`hass.localize`), so it follows every language HA has. Pick the closest
  existing key; when none fits, change the UI (drag to reorder instead of
  "move up/down" buttons) rather than adding a translation file.
- A button is active only when its entity's state is `on`. Scenes
  (`scene.*`) have no state; the README's "Setting up scenes" recipe gives
  each scene a helper, set by the scene, and a template switch on that
  helper whose `turn_on` activates the scene. Its shorter variant uses the
  helper as the button, with `tap_action` `scene.turn_on`.
- Config: `buttons` (0–n, an entity id is short for `{ entity }`), optional
  card `title`, `center_title` (default `false`, left aligned), `show_name`
  (default `true`; `false` hides the names and makes the buttons narrower
  and lower) and `color`. Per button: `entity`, `name`, `secondary`, `icon`,
  `color`, `tap_action` (default `toggle`), `hold_action`,
  `double_tap_action`.
- Buttons are flat ovals (no border or shadow, fully round ends), with as
  much space beside the icon as above it (9px with names, 6px without).
  Below the text: 17px with names (the owner chose it over 27px), 22px
  without.
  An `aspect-ratio` to keep wide buttons taller than wide was tried and
  rejected.
- `name` (the primary text, kept from HA's naming) and `secondary` can be
  templates: text with `{{`, `{%` or `{#` (`isTemplate`). The card
  subscribes with `render_template` (variables: `entity`), keeps results by
  `<index>.<field>`, resubscribes on `setConfig` and when the card is
  attached again, and unsubscribes when it's removed. Plain text doesn't
  subscribe. An empty `name` result falls back to the entity's name.
- All buttons in a card are equally wide: each holds hidden copies of every
  name and secondary text (`.sizer`, stacked in one grid cell), so the
  widest text sets the width for all. CSS only, no measuring. They shrink
  equally, with ellipsis, when space runs out.
- Active color: the button's `color`, else the card's, else `primary`
  (`--primary-color`). Colors are HA's `ui_color` names (mapped to
  `var(--<name>-color)`) or any CSS color.
- No buttons and no title renders nothing, like a stack without cards; it
  doesn't throw. A title alone shows the card.
- A missing entity shows greyed out with `mdi:help-circle-outline` and its
  entity id, and isn't clickable. `unavailable`/`unknown` is greyed out but
  stays clickable.
- README images are in `images/`: `main.png` at the top, `default_color.png`
  (titles, no names), `colors.png` (colors) and `template_text.png`
  (templates). The owner takes them from the `dev/` dashboard; update the
  README when one is added or removed.
- Sections dashboards: `getGridOptions()` returns
  `{ columns: 12, min_columns: 3 }`; rows follow the content.

## Custom card essentials

How a dashboard card talks to Home Assistant. Check against the reference
implementation before inventing something: HA's frontend repo
(`home-assistant/frontend`), especially `src/panels/lovelace/cards/`
(`hui-tile-card.ts`, `hui-button-card.ts`, `hui-stack-card.ts`) and
`src/common/` (colors, translations). The backend source is in the test
container under `/usr/src/homeassistant/homeassistant/`, the built frontend
under `site-packages/hass_frontend/`.

**The card contract**

- `setConfig(config)` runs first and on every editor change, on the **same
  element** (the editor preview isn't recreated). Throwing shows an error card.
  Normalize defaults here.
- `set hass(hass)` runs on **every state change in Home Assistant**, not just
  the buttons' entities. Keep it cheap: the card compares each button's
  entity object by reference and only passes changed ones on.
- `getCardSize()` – masonry height in 50px units. `getGridOptions()` –
  sections grid; 12 columns is one dashboard column, and a section with
  `column_span: N` has 12×N columns. Stored `grid_options` in a card's config
  override it, and `min_columns` only limits the editor.
- `static getConfigElement()` / `getStubConfig(hass)` for the editor and card
  picker; `window.customCards.push(...)` lists the card in the picker.
- Card-mod and UIX are applied via their `applyToElement` once per config.

**Translations and theme**

- Editor labels:
  `hass.localize("ui.panel.lovelace.editor.card.generic.<field>")` and
  similar keys. `ui.panel.lovelace.editor.*` is loaded while a card
  editor is open, `ui.common.*` always. Look keys up in the test container's
  `hass_frontend/static/translations/`.
- Theme: style with HA's CSS variables (`--primary-text-color`,
  `--primary-color`, `--divider-color`, `--ha-card-*`, `--<color>-color`) so
  themes and dark mode work.

**The editor**

- Fire `config-changed` (bubbles, composed) with the whole config.
- `ha-form` with selectors: `entity` (with `domain`), `text`, `icon` (with
  `context: { icon_entity: "entity" }` for the entity's icon as placeholder),
  `boolean`, `ui_color` (HA's color names), `ui_action` (`default_action`).
  `computeLabel` names the fields.
- `ha-form` sends **every** field on each change, cleared text as `""` and
  switched off booleans as `false`. Only store what the user actually set
  (`compact` in the editor drops those), or defaults end up hard-coded in
  their config.
- Keep schema objects stable between renders; new objects make ha-form
  rebuild its fields and lose focus.
- Other HA elements: `ha-card`, `ha-expansion-panel`, `ha-entity-picker`,
  `ha-icon`, `ha-state-icon`, `ha-icon-button`, `ha-sortable` (fires
  `item-moved` with `{ oldIndex, newIndex }` and puts the DOM back itself;
  loaded by HA's edit card dialog). They exist at runtime only; tests run
  without them.

**Interaction and accessibility**

- Fire `hass-action` with `{ config, action: "tap" | "hold" | "double_tap" }`
  instead of handling actions yourself. HA reads `config.entity` and
  `config.<action>_action`, and falls back to `more-info` when the action is
  missing, so always pass `tap_action`. HA handles every action type; old
  `perform_action` (underscore) is normalized to `perform-action`.
- A clickable button needs `role="button"`, `tabindex="0"`, Enter/Space and a
  visible focus outline, and none of it when there's no action. Toggle
  buttons also get `aria-pressed`.

## Home Assistant specifics

- From HA 2026.11, HACS is built in as the **Marketplace** (still reads
  `hacs.json`, category `plugin`). The card supports HA 2026.4+, so docs
  mention both.
- The card is in HACS's default list (hacs/default#15005), so users find it
  by searching; it doesn't need to be added as a custom repository.

## Test environment (dev/)

- HA at http://localhost:8125, login skipped from localhost. Dashboard
  "Scene card" (`dev/config/dashboards/scenes.yaml`) has a view per area.
- The compose project is named `ha-scene-card`; without a name, compose
  uses the folder name `dev` and replaces other projects' containers.
- `dev-loader.js` imports the card with `?t=<now>`, because HA serves
  `/local/` with a 31 day cache. Other files in `www/` need a hard refresh.
- Scenes are `input_boolean.<morning|night|dinner|movie|party>_scene`
  (party has a long name, for ellipsis). The demo integration adds lights
  (`light.ceiling_lights`, `light.kitchen_lights`, ...) and switches
  (`switch.ac`, `switch.decorative_lights`).
- Changes to `configuration.yaml` need `docker restart ha-scene-card-ha`.
  Check config with
  `docker exec ha-scene-card-ha python3 -m homeassistant --script check_config -c /config`.
